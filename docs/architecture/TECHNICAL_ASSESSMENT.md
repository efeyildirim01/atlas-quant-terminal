# Technical Assessment — Phase 2 (2026-10-16)

## Architecture
A **modular monolith**: one FastAPI application (`apps/api`) with isolated domain packages, plus one
Next.js application (`apps/web`). Background work (ingestion, report generation) runs as worker
entry points in the same codebase (`app/workers`), started as separate processes. Microservices are
deferred until a measured scaling need exists.

```
apps/api/app
  core/          config, db engine, logging, correlation ids, rate limiting, security helpers
  auth/          password hashing, sessions, CSRF, RBAC dependencies
  models/        SQLAlchemy 2 ORM (decimal-safe, point-in-time columns)
  schemas/       Pydantic v2 API contracts + financial envelope
  integrations/  provider adapters (fixture, CSV, EVDS, licence gates) + source catalog
  services/      ingestion, data quality, search, market/equity/fund services
  repositories/  DB reads that return analysis-ready frames (quality-filtered)
  analytics/     pure, deterministic financial functions (no I/O, no clock)
  api/v1/        HTTP routers
  workers/       CLI / background jobs (ingest, seed users)
  ai/            reserved for Milestone 6 (tool registry), intentionally empty
```

Rules: financial formulas live only in `analytics/`. React components only render numbers the API
computed. Every financial response is wrapped in an envelope with sources, as-of, quality and
methodology.

## Data-source feasibility (summary)
Only **EVDS** offers an official API with reuse rights, and it needs a key we do not have yet.
BIST and KAP need contracts. TEFAS has no official API. See `docs/data-sources/SOURCE_INVENTORY.md`.
**Consequence:** Milestone 2's "at least one permitted real source" criterion is **not met**. The EVDS
adapter is implemented and unit-tested against mocked responses. It becomes the first real source
once a key is configured.

## Licensing risks
1. Displaying BIST prices without a vendor licence is an infringement risk. The UI therefore shows
   only fixture or user-supplied data, both labelled.
2. Computing indices from BIST data needs a separate licence, so even with an EOD licence the
   fixture "index" must not be replaced by a self-computed BIST index.
3. Scraping TEFAS or KAP is excluded.
4. EVDS reuse requires attribution. The envelope carries an `attribution` field.
5. Investment-advice perimeter (SPK): no recommendations, no order routing, and signal output is
   held at "insufficient evidence".

## Database
PostgreSQL in production (TimescaleDB optional for `market_prices`/`fund_nav` hypertables once row
counts justify it). SQLAlchemy models are portable, so local development and the test suite run on
SQLite. Migrations are generated by Alembic and also rendered as PostgreSQL DDL in offline mode, to
catch dialect problems without a running server.

Conventions:
- Money, prices and NAV use `NUMERIC(24,8)` and are read as `Decimal`. Analytics convert to float64
  (relative error ~1e-16, which is immaterial for statistics) and say so in the methodology.
- Timestamps are stored in **UTC** (`timestamptz`). Exchange-local time is `Europe/Istanbul`
  (UTC+3, no DST since 2016). Daily bars are stamped at the 18:00 Istanbul session close (15:00 UTC).
- Point-in-time: `ingestion_timestamp`, `publication_timestamp` and `revision_version` columns
  preserve when data became known.
- Instrument identity is `(symbol, instrument_type, exchange)`. Symbols are not globally unique.

## Environment constraints found during implementation
- No Docker, PostgreSQL or Redis on this machine. An embedded PostgreSQL (`pgserver`) failed because
  of Windows path-length limits. `docker-compose.yml` is provided but **has not been executed**.
- Python venv creation and npm install scripts fail inside the app-sandboxed folder. The README shows
  the normal commands, which work on a regular checkout.

## Implementation sequence (this iteration)
1. Monorepo layout, config, logging, correlation IDs, rate limiting
2. ORM models + Alembic migration + data-source catalog
3. Auth (sessions, CSRF, RBAC) + portfolio isolation tests
4. Ingestion → quality engine → storage → data-health endpoint
5. Analytics library (`calculate_*`) with reference and property-based tests
6. Vertical slice: search → stored history → chart → metrics → source metadata
7. CI workflow, Dockerfiles, compose file, docs
